# ADR-001: Start with Git, Docker Baseline, and Spreadsheet/Power Query Profiling

- **Status:** Accepted
- **Date:** 2026-11-23
- **Milestone:** `v0.1`

## Context
I am transitioning from a Data Science background toward **Analytics Engineering** and **Data Engineering** at a pace of **11 hours per week**, building projects in this repository (`v0.1` through `Final`). Early data work often starts with messy raw files (such as spreadsheets or CSVs) and local services running in containers, while data engineering spans the lifecycle (*Generation, Storage, Ingestion, Transformation, Serving*) and undercurrents (*Security, Data Management, DataOps, Data Architecture, Orchestration, Software Engineering*). Jumping straight into complex tools or ad-hoc scripts without version-control hygiene, reproducible containers, or initial schema profiling creates avoidable rework, hidden assumptions, and risk of leaking secrets[cite: 2, 3, 5].

## Decision
Start Phase 1 by consolidating a clean **Git** and **Docker / Docker Compose** baseline (including local containerized services such as MongoDB/app labs) alongside **spreadsheet and Power Query profiling/cleaning** before scaling into relational databases, Python scripts, cloud data warehouses, dbt, Power BI, and PySpark[cite: 2, 3, 5]. Every significant decision and mistake will be tracked via `README.md`, `ADR-001.md`, and a learning error log (`LEARNING_LOG.md`)[cite: 2, 4, 5].

## Alternatives Considered
- **Jump straight into Python/SQL/cloud/distributed tools:** Faster to experiment with code, but risks skipping data profiling, environment reproducibility, cost awareness, and architectural trade-off thinking (*architecture first, technology second*)[cite: 2].
- **Rely on manual, undocumented edits:** Fast for a one-off check, but hard to reproduce, audit, or debug when schemas or requirements change[cite: 2].

## Consequences & Trade-Offs (Pillar Alignment)
- **Reis & Housley (*Fundamentals of Data Engineering*):** Starting with local containers, version control, and spreadsheet profiling is a low-cost, **reversible ("two-way door") decision** that separates data/application concerns cleanly for local learning and keeps early scope focused on real problems rather than "resume-driven development"[cite: 2].
- **Konieczny (*Data Engineering Design Patterns*):** Inspecting raw rows, nullability, types, and duplicates early sets the foundation for **repeatable ingestion/cleaning steps**, explicit data quality checks, and clear boundaries between raw/curated data[cite: 2, 3].
- **Dalio (*Principles*):** Pairing structured deliverables with a mistake log supports systematic diagnosis (*problem -> root cause -> plan*) rather than relying on memory or raw motivation[cite: 4, 5].
- **Known Limitations:** Spreadsheets, Power Query, and single-machine Docker setups are not meant for high-volume production storage, distributed batch/stream scale, or full production orchestration—those capabilities will be introduced intentionally in later phases as the architecture evolves[cite: 2, 5].
